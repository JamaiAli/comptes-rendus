Journal de bord : administration SELinux sur Gentoo Hardened

Ce document reprend chaque commande exécutée depuis le début du TD, explique précisément ce qu'elle fait et pourquoi on l'utilise à ce moment précis, et relie chaque manipulation à une question du TD.

hôte : briffaut ip : 192.168.106.139 hyperviseur : VMware Workstation
identité rôle type — un contexte SELinux s'écrit toujours identité:rôle:type, et cette coloration est utilisée dans tout le document, y compris dans les sorties de terminal.

Contexte du TD pourquoi

Avant de taper la moindre commande, il faut comprendre quel problème SELinux résout.

Sous Linux « classique », le contrôle d'accès est discrétionnaire (DAC) : les droits `rwx` et le propriétaire d'un fichier décident de tout, et root passe outre toutes les règles. SELinux ajoute une couche de contrôle d'accès obligatoire (MAC) : chaque processus et chaque objet (fichier, socket, périphérique...) reçoit un contexte de sécurité, et une politique centrale décide quels contextes ont le droit d'interagir avec quels autres — même root peut se voir refuser un accès si la politique ne l'autorise pas explicitement.

La VM utilisée est une Gentoo Hardened, une distribution Gentoo durcie où SELinux est activé nativement avec la politique strict de refpolicy. Le TD se déroule en deux temps : d'abord comprendre le modèle (identités, rôles, types, modes permissif/enforcing), puis écrire un module de politique sur mesure pour confiner l'application claws-mail.

01 · Mise en place de l'environnement

Avant de pouvoir taper la moindre commande SELinux, il faut faire tourner la VM et pouvoir s'y connecter confortablement.

ÉTAPEDécompression et import de la VM

L'archive gentoo-hardened-selinux.zip a été décompressée puis importée dans VMware Workstation. Au premier démarrage, VMware a affiché un avertissement :

POURQUOI CETTE POPUP ?

VMware associe à chaque VM une adresse MAC et un UUID uniques. Quand le dossier de la VM apparaît « de nulle part » (ici : extrait d'un zip), VMware ne sait pas s'il s'agit d'une VM déplacée (garder les mêmes identifiants) ou copiée (en générer de nouveaux pour éviter un conflit réseau avec l'original). On a répondu « I Copied It », le choix correct puisqu'il s'agit bien d'une copie extraite d'une archive.

02 · Identités et rôles SELinux

Avant de lire le moindre contexte, il faut connaître le vocabulaire que la politique strict utilise par défaut.

IdentitéRôlesDescription
system_usystem_rProcessus systèmes (non-interactifs). Jamais utilisée pour un utilisateur humain.
user_uuser_rUtilisateur générique sans privilège. C'est le mapping par défaut (__default__).
staff_ustaff_r, sysadm_rAdministrateurs qui font aussi des activités « normales » d'utilisateur.
sysadm_usysadm_rAdministrateurs qui ne font que de l'administration système. Déconseillée en usage courant.
rootstaff_r, sysadm_rIdentité spéciale de root. Démarre en staff_r, doit explicitement basculer en sysadm_r.
POINT CLÉ À RETENIR

Root n'est pas automatiquement administrateur SELinux. Il a accès aux deux rôles staff_r et sysadm_r, mais démarre par défaut en staff_r — un rôle « utilisateur avancé », pas encore le rôle qui autorise la gestion de la politique. C'est exactement ce qu'on observe à la section 05.

03 · Contextes objets Q1

Un contexte objet décrit un fichier, un répertoire ou tout autre élément passif du système — pas un processus.

SSH — user (session standard)
user@briffaut ~ $ ls -Z /
   system_u:object_r:bin_t bin
  system_u:object_r:boot_t boot
system_u:object_r:device_t dev
   system_u:object_r:etc_t etc
system_u:object_r:home_root_t home
   system_u:object_r:lib_t lib
   system_u:object_r:lib_t lib64
system_u:object_r:usr_t opt
  system_u:object_r:proc_t proc
root:object_r:user_home_dir_t root
system_u:object_r:var_run_t run
   system_u:object_r:bin_t sbin
 system_u:object_r:sysfs_t sys
   system_u:object_r:tmp_t tmp
   system_u:object_r:usr_t usr
   system_u:object_r:var_t var  (sortie tronquée)

user@briffaut ~ $ ls -Z /root
ls: impossible d'ouvrir le répertoire '/root': Permission non accordée

user@briffaut ~ $ ls -Z /etc/shadow /etc/passwd
system_u:object_r:shadow_t /etc/shadow
   system_u:object_r:etc_t /etc/passwd

user@briffaut ~ $ ls -Z /bin/login
system_u:object_r:login_exec_t /bin/login
POURQUOI `ls -Z` ?

L'option -Z demande à ls d'afficher, en plus du nom de fichier, son contexte objet : identité:object_r:type. Le rôle est presque toujours figé à object_r pour un objet (les rôles servent à contrôler des processus, pas des fichiers) — c'est le champ type qui porte toute l'information utile : c'est lui que la politique consulte pour décider si tel processus peut lire, écrire ou exécuter ce fichier.

À NOTER : `/root` refusé

Le refus sur /root n'a rien à voir avec SELinux ici — c'est un simple droit Unix classique (répertoire personnel de root, non accessible en lecture à un autre utilisateur). Bon réflexe à garder : toujours se demander si un refus vient des droits Unix (DAC) ou de SELinux (MAC) avant de chercher une explication compliquée — on retombera exactement sur ce piège un peu plus loin.

Q1Quel est le contexte associé à chacun de ces éléments ?

ÉlémentContexte objet
/etc/shadowsystem_u:object_r:shadow_t
/etc/passwdsystem_u:object_r:etc_t

À NOTER /etc/passwd n'a pas de type dédié comme /etc/shadow — il reste dans le type générique etc_t. C'est cohérent avec la sensibilité relative des deux fichiers : shadow contient les hachages de mots de passe, passwd non.

POURQUOI `ps auxZ` ET `id -Z` ?

ps auxZ ajoute la colonne LABEL (contexte sujet) à la liste des processus — utile pour comparer des familles entières de processus d'un coup d'œil. id -Z affiche uniquement le contexte du shell courant, plus rapide quand on veut juste vérifier sa propre session (ce qu'on va faire en boucle dans la suite du TD).

CORRECTION EN COURS DE ROUTE

Une hypothèse initiale plaçait le compte user sous l'identité user_u (le mapping « générique » par défaut décrit dans le tableau des identités). La sortie réelle de id -Z montre staff_u:staff_r:staff_t : sur cette image précise, le compte user est explicitement mappé sur staff_u. Ça illustre bien l'esprit du TD : la table des identités donne les possibilités par défaut de la politique, mais le mapping réel (semanage login -l, vu plus loin) peut avoir été personnalisé — on vérifie toujours, on ne suppose jamais.

BONUS OBSERVÉ la session ouverte via SSH tourne sous sshd_t pendant l'authentification, puis bascule en staff_t pour le shell — alors que le login console passe par local_login_t. Deux chemins d'authentification, deux contextes différents, même utilisateur final.

05 · Changement de rôle et statut de la politique Q3 – Q5

On se reconnecte en root pour observer le rôle par défaut, puis on bascule explicitement en administrateur SELinux.

SSH — root
briffaut ~ # id -Z
root:staff_r:staff_t

briffaut ~ # newrole -r sysadm_r
Mot de passe : azerty

briffaut ~ # id -Z
root:sysadm_r:sysadm_t
POURQUOI `newrole` ET PAS UN SIMPLE `su` ?

su/sudo changent l'identité Unix (uid) ; newrole -r change le rôle SELinux du shell courant, en gardant la même identité. C'est exactement pour ça que root démarre en staff_r : ça force explicitement à demander le rôle sysadm_r avant toute opération d'administration de la politique, plutôt que de l'avoir automatiquement dès le login. C'est une friction volontaire — un garde-fou.

Q3Quel est le contexte associé à votre session (avant tout changement) ?

RÉPONSE root:staff_r:staff_t

Q4Quel rôle faut-il prendre pour devenir super-administrateur SELinux ?

RÉPONSE sysadm_r

Q5aQuel est le nouveau contexte après newrole ?

RÉPONSE root:sysadm_r:sysadm_t
SSH — root (sysadm_r)
briffaut ~ # sestatus
SELinux status:                 enabled
Loaded policy name:              strict
Current mode:                    permissive
Mode from config file:           permissive
Policy MLS status:               disabled
Policy deny_unknown status:      allowed

briffaut ~ # setenforce 1
briffaut ~ # sestatus
Current mode:                    enforcing
Mode from config file:           permissive

briffaut ~ # setenforce 0
POURQUOI TESTER `setenforce` ICI ?

Ce test (non demandé littéralement par l'énoncé à cette étape, mais fait spontanément) montre une distinction importante : « mode courant » et « mode par défaut au démarrage » sont deux valeurs indépendantes. setenforce change uniquement le mode courant, en mémoire, jusqu'au prochain redémarrage — le fichier /etc/selinux/config (qui fixe le mode par défaut) n'est jamais modifié par cette commande.

Q5bStatus, type, mode par défaut, mode courant — que signifient-ils ?

ChampValeur relevéeSignification
StatusenabledSELinux est chargé et actif dans le noyau.
Type (policy)strictPolitique la plus restrictive de refpolicy : tout processus est confiné, aucun type « unconfined » par défaut.
Mode par défautpermissiveCe que /etc/selinux/config applique à chaque démarrage.
Mode courantpermissiveCe qui est réellement actif en mémoire à l'instant présent (modifiable à chaud avec setenforce).
À NOTER le système tourne en permissif par défaut : SELinux évalue toutes les règles et journalise les refus, mais ne bloque jamais rien. Utile en développement/formation, dangereux en production.

06 · Permissif vs enforcing, à deux terminaux Q5 — test pratique

Le but : observer concrètement la différence entre « SELinux journalise » et « SELinux bloque », avec deux sessions ouvertes en même temps.

⚠ ERREUR DE PARCOURS INSTRUCTIVE

Première tentative : TERM_B ouvert avec le compte user (non-root), puis cat /etc/shadow → Permission non accordée. Ce refus n'a rien à voir avec SELinux : /etc/shadow est lisible uniquement par root au niveau des droits Unix classiques (DAC), donc un utilisateur normal est bloqué avant même que SELinux n'intervienne. Le test du TD n'a de sens qu'en comparant deux sessions root — ainsi les droits Unix laissent passer, et c'est vraiment SELinux (MAC) qui décide seul du résultat.

TERM_B corrigé : une nouvelle connexion SSH en root.

TERM_B — root (nouvelle session)
briffaut ~ # id -Z
root:staff_r:staff_t
POURQUOI CE CONTEXTE, ET PAS `sysadm_r` ?

Ça confirme un point essentiel du TD : newrole ne change le rôle que du processus shell qui l'a exécuté — pas de l'identité root en général. Une toute nouvelle connexion SSH démarre un nouveau shell, qui repart du rôle par défaut (staff_r), même si un autre terminal de la même identité root est actuellement en sysadm_r. Le changement de rôle ne se propage jamais aux autres sessions.

TERM_A — sysadm_r (contrôle)
briffaut ~ # setenforce 0
→ repasse en mode permissif
TERM_B — staff_r (testé)
briffaut ~ # cat /etc/shadow
→ lecture réussie (confirmé)
POURQUOI ÇA PASSE ALORS QUE LE TYPE NE CORRESPOND PAS ?

En mode permissif, SELinux évalue quand même la règle (et aurait dit non), mais n'applique pas le refus — il se contente de le journaliser (section suivante). Les droits Unix, eux, passent puisque TERM_B est aussi root. Résultat : la lecture réussit malgré l'absence de règle allow entre staff_t et shadow_t.

TERM_A — sysadm_r
briffaut ~ # setenforce 1
→ repasse en mode enforcing
TERM_B — staff_r
briffaut ~ # cat /etc/shadow
→ Permission denied (attendu) à reconfirmer
À REFAIRE / CONFIRMER

Cette dernière étape (bascule en enforcing puis nouvelle tentative de lecture) a été enchaînée sans coller la sortie exacte du terminal. Le comportement attendu — un Permission denied franc, cette fois réellement bloqué — reste à vérifier explicitement avant de conclure le test, pour avoir une preuve écrite comparable à celle du mode permissif.

07 · Lire une trace AVC dans `dmesg` Q5 — traces

Un refus SELinux, même en permissif, laisse une trace exploitable dans les logs noyau — c'est l'outil de diagnostic principal.

TERM_A — sysadm_r
briffaut ~ # setenforce 0
briffaut ~ # dmesg -c
→ vide le tampon de traces noyau pour repartir propre
TERM_B — staff_r
briffaut ~ # cat /etc/ssh/ssh_host_key
cat: /etc/ssh/ssh_host_key: Aucun fichier ou dossier de ce type

briffaut ~ # ls -Z /etc/ssh/*key*
system_u:object_r:sshd_key_t /etc/ssh/ssh_host_ecdsa_key
system_u:object_r:sshd_key_t /etc/ssh/ssh_host_ecdsa_key.pub
system_u:object_r:sshd_key_t /etc/ssh/ssh_host_ed25519_key
system_u:object_r:sshd_key_t /etc/ssh/ssh_host_ed25519_key.pub
system_u:object_r:sshd_key_t /etc/ssh/ssh_host_rsa_key
system_u:object_r:sshd_key_t /etc/ssh/ssh_host_rsa_key.pub

briffaut ~ # cat /etc/ssh/ssh_host_ed25519_key
POURQUOI `ssh_host_key` N'EXISTAIT PAS ?

Le TD a été écrit à une époque où SSH ne générait qu'une seule clé d'hôte, de type RSA, littéralement nommée ssh_host_key. Les versions modernes d'OpenSSH génèrent plusieurs types de clés en parallèle (RSA, ECDSA, Ed25519) avec des noms explicites. ls -Z /etc/ssh/*key* permet de retrouver le fichier équivalent aujourd'hui — et confirme au passage que tous les fichiers de clés d'hôte SSH partagent le même type sshd_key_t, peu importe l'algorithme.

TERM_A — sysadm_r
briffaut ~ # dmesg
audit: type=1400 avc:  denied  { read } for  pid=2210 comm="cat"
  name="ssh_host_ed25519_key" dev="sda2" ino=141611
  scontext=root:staff_r:staff_t tcontext=system_u:object_r:sshd_key_t
  tclass=file permissive=1
audit: type=1400 avc:  denied  { open } for  pid=2210 comm="cat"
  path="/etc/ssh/ssh_host_ed25519_key" dev="sda2" ino=141611
  scontext=root:staff_r:staff_t tcontext=system_u:object_r:sshd_key_t
  tclass=file permissive=1

LectureDécomposition de la trace

ChampSens
avc: deniedSELinux a refusé cet accès (mais ne l'a pas bloqué, on est en permissif).
{ read }, { open }Deux traces distinctes car cat effectue deux appels système différents pour lire un fichier.
comm="cat"Le programme à l'origine de l'accès.
scontext=...Contexte sujet : le processus qui demande l'accès (root:staff_r:staff_t).
tcontext=...Contexte objet cible : le fichier visé (system_u:object_r:sshd_key_t).
tclass=fileClasse de l'objet cible (ici : fichier normal).
permissive=1Confirme que le refus a été journalisé sans être appliqué.
CONCLUSION en enforcing, staff_t n'ayant aucune règle allow vers sshd_key_t, cette lecture aurait été bloquée — exactement le même mécanisme que pour /etc/shadow plus haut.
