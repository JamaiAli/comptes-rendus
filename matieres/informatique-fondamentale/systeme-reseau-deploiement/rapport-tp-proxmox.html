Maquette réseau routée sous Proxmox

Compte rendu de TP : une box Debian 13 en conteneur LXC qui route deux réseaux clients vers un pare-feu OPNsense, avec adressage statique, IP forwarding, masquerade NAT, DHCP et DNS.

Topologie logique. Les bridges (en couleur) sont les « switchs virtuels », les machines (en blanc) s'y branchent.

Pourquoi deux routeurs empilés ?

OPNsense joue le rôle du pare-feu d'entreprise : il fait la frontière avec le réseau de l'école. La box joue le rôle d'un routeur interne qui segmente les postes clients en deux réseaux distincts. Cette architecture en couches est courante : un pare-feu périmétrique, puis des routeurs ou switchs L3 qui découpent le réseau interne en sous-réseaux.

3Plan d'adressage

Chaque réseau est un /24 : les 24 premiers bits identifient le réseau, les 8 derniers identifient la machine. Cela donne 256 adresses dont 254 utilisables (la première est l'adresse du réseau, la dernière l'adresse de broadcast).

RéseauAdresse réseauMasquePasserellePlage DHCPBroadcast
vmbr110.0.0.0/24255.255.255.010.0.0.254 (OPNsense)Gérée par OPNsense10.0.0.255
vmbr210.10.2.0/24255.255.255.010.10.2.1 (box)10.10.2.100 – .20010.10.2.255
vmbr310.10.3.0/24255.255.255.010.10.3.1 (box)10.10.3.100 – .20010.10.3.255
Conventions de ce plan
  • Sur les réseaux clients, la passerelle prend l'adresse .1. Sur vmbr1, l'OPNsense utilise .254 : les deux conventions (première ou dernière adresse) sont courantes, l'important est que la passerelle soit fixe et connue.
  • La plage DHCP commence à .100 : les adresses .2 à .99 restent libres pour d'éventuels serveurs en IP fixe, sans risque de conflit avec un bail DHCP.
  • Tous ces réseaux sont dans 10.0.0.0/8, une plage privée (RFC 1918). Elle n'est pas routable sur Internet, d'où le besoin de NAT.
Pourquoi la box a une IP statique côté clients et DHCP côté OPNsense ?

Côté vmbr2 et vmbr3, la box est la passerelle et le serveur DHCP : son adresse doit être fixe et connue, sinon les clients ne sauraient pas où envoyer leurs paquets. Côté vmbr1, la box est un simple client de l'OPNsense, son adresse peut donc être distribuée par DHCP. En production on lui fixerait plutôt une réservation DHCP ou une IP statique pour pouvoir créer des routes vers elle.

4Bridges Proxmox

Un Linux bridge (vmbrX) est un switch virtuel dans le noyau de l'hyperviseur. Chaque carte réseau virtuelle d'une machine (VM ou conteneur) est un port branché sur un bridge. Deux machines sur le même bridge sont sur le même réseau de niveau 2 : elles se voient en Ethernet et reçoivent les broadcasts l'une de l'autre.

Seul vmbr0 sort de la machine physique. vmbr1, vmbr2 et vmbr3 sont des réseaux internes totalement isolés.

Création

Dans l'interface web : Datacenter › nœud › System › Network › Create › Linux Bridge. Pour vmbr2 et vmbr3 :

  • IPv4/CIDR vide : l'hyperviseur n'a pas besoin d'IP sur ces réseaux, il se contente de commuter les trames.
  • Bridge ports vide : aucune carte physique, le réseau reste interne.
  • Cliquer sur Apply Configuration pour appliquer sans redémarrer.

Équivalent dans /etc/network/interfaces de l'hôte :

/etc/network/interfaces (hôte Proxmox) 
auto vmbr2
iface vmbr2 inet manual
    bridge-ports none
    bridge-stp off
    bridge-fd 0

auto vmbr3
iface vmbr3 inet manual
    bridge-ports none
    bridge-stp off
    bridge-fd 0
Ce que veulent dire ces options
  • inet manual : l'interface existe mais sans adresse IP.
  • bridge-ports none : aucune interface physique n'est rattachée.
  • bridge-stp off : pas de Spanning Tree, inutile ici puisqu'il n'y a pas de boucle possible.
  • bridge-fd 0 : pas de délai d'attente avant que le bridge commence à transmettre.
Pourquoi l'isolation compte

Comme vmbr2 n'a aucun lien avec l'extérieur, client2 n'a qu'une seule porte de sortie : la box. C'est exactement ce qu'on veut démontrer. Tout le trafic de client2 passe par un point de contrôle unique, où on peut router, traduire et filtrer.

5Création des conteneurs

Les trois machines Debian sont des conteneurs LXC créés à partir du template Debian 13 récupéré sur le stockage NFS. Un template est un modèle figé qui sert de base à chaque nouvelle machine.

Conteneur LXC ou machine virtuelle ?

Une VM émule une machine complète avec son propre noyau. Un conteneur LXC partage le noyau de l'hyperviseur et n'isole que les processus, le système de fichiers et le réseau. Il démarre en quelques secondes et consomme très peu de ressources, ce qui est idéal pour une maquette réseau avec plusieurs machines.

Branchement des cartes réseau

Pour un conteneur, c'est Proxmox qui gère la configuration réseau : on la définit dans conteneur › Network, et Proxmox l'écrit lui-même dans le conteneur à chaque démarrage. Équivalent en ligne de commande sur l'hôte :

shell de l'hôte Proxmox 
# box : une carte par réseau
pct set 100 \
  --net0 name=eth0,bridge=vmbr1,ip=dhcp \
  --net1 name=eth1,bridge=vmbr2,ip=10.10.2.1/24 \
  --net2 name=eth2,bridge=vmbr3,ip=10.10.3.1/24

# clients : DHCP sur leur réseau
pct set 101 --net0 name=eth0,bridge=vmbr2,ip=dhcp
pct set 102 --net0 name=eth0,bridge=vmbr3,ip=dhcp

Pourquoi eth0@if42 ?

Chaque carte d'un conteneur est une paire veth : un « câble virtuel » avec un bout dans le conteneur (eth0) et l'autre sur l'hôte, branché au bridge. Le suffixe @if42 donne le numéro d'interface du bout côté hôte. C'est d'ailleurs ce détail qui a permis d'identifier que les machines étaient des conteneurs.

IPv4 sur « DHCP », pas sur « Static » vide

Si le champ IPv4 de la carte n'est pas réglé sur DHCP, Proxmox ne configure aucune adresse dans le conteneur : il ne reste qu'une IPv6 link-local fe80:: et aucune route. Toute modification à la main de /etc/network/interfaces dans le conteneur est écrasée au prochain démarrage.

Nom d'hôte de chaque conteneur :

hostnamectl set-hostname box        # client2 / client3 selon le conteneur

6Adressage de la box

La box a trois interfaces, une par réseau. Leur configuration est définie dans Proxmox (section 5), qui génère le fichier suivant dans le conteneur :

/etc/network/interfaces (box, généré par Proxmox) 
auto lo
iface lo inet loopback

auto eth0
iface eth0 inet dhcp           # vmbr1 : adresse donnée par OPNsense

auto eth1
iface eth1 inet static         # vmbr2 : passerelle des clients 10.10.2.0/24
    address 10.10.2.1/24

auto eth2
iface eth2 inet static         # vmbr3 : passerelle des clients 10.10.3.0/24
    address 10.10.3.1/24
Lecture ligne par ligne
  • auto eth1 : active l'interface au démarrage.
  • inet static : adresse IPv4 fixe.
  • address 10.10.2.1/24 : adresse et masque en notation CIDR.
  • Aucune passerelle sur eth1 et eth2 : la seule route par défaut de la box doit pointer vers l'OPNsense, et elle est reçue par DHCP sur eth0.

Relevé sur la box pendant le TP :

root@box:~# ip -br a ; ip route

Les routes « connectées »

Dès qu'on met une adresse sur une interface, le noyau ajoute automatiquement la route vers le réseau correspondant (proto kernel). La box sait donc déjà joindre 10.10.2.0/24 et 10.10.3.0/24 sans aucune route manuelle. Pour tout le reste, elle utilise la route par défaut vers l'OPNsense en 10.0.0.254.

7Routage et IP forwarding

Par défaut, Linux se comporte comme une machine terminale : s'il reçoit un paquet qui ne lui est pas destiné, il le jette. Pour qu'il transmette les paquets d'une interface à une autre, il faut activer l'IP forwarding.

box 
echo "net.ipv4.ip_forward=1" > /etc/sysctl.d/99-forward.conf
sysctl --system
sysctl net.ipv4.ip_forward     # doit afficher = 1
Spécificité Debian 13

Depuis Debian 13 (Trixie), le fichier /etc/sysctl.conf n'est plus lu par défaut. Les paramètres doivent être placés dans un fichier de /etc/sysctl.d/. Écrire dans sysctl.conf fonctionnerait en apparence avec sysctl -p, mais serait perdu au redémarrage.

Ce que fait la box quand un paquet arrive :

Chemin de décision d'un paquet traversant la box.

Routage entre client2 et client3

Avec le forwarding activé, la box route aussi entre ses deux réseaux clients : client2 peut joindre client3 directement, sans passer par l'OPNsense, puisque les deux réseaux sont connectés à la box. C'est le comportement d'un routeur « ouvert ». Si on veut isoler les deux réseaux, il faut ajouter des règles de filtrage (voir section 14).

8NAT et masquerade

Le forwarding seul ne suffit pas. Quand client2 envoie un paquet vers Internet, la box le transmet bien à l'OPNsense, mais l'OPNsense ne connaît pas le réseau 10.10.2.0/24 : il ne sait pas où renvoyer la réponse. Le masquerade résout ce problème en remplaçant l'adresse source des paquets sortants par l'adresse de la box.

/etc/nftables.conf (box) 
#!/usr/sbin/nft -f
flush ruleset

table ip nat {
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    oifname "eth0" ip saddr 10.10.2.0/23 masquerade
  }
}
apt install -y nftables
systemctl enable --now nftables
nft list ruleset       # vérification
Décryptage de la règle
  • flush ruleset : on repart d'une configuration vide à chaque chargement.
  • table ip nat : une table pour IPv4, nommée nat (le nom est libre).
  • type nat hook postrouting : la chaîne s'exécute juste avant l'émission du paquet, après la décision de routage. C'est là qu'on modifie l'adresse source.
  • priority srcnat : nom symbolique de la priorité 100, la priorité standard du NAT source.
  • policy accept : la chaîne ne bloque rien, elle ne sert qu'à traduire.
  • oifname "eth0" : uniquement pour les paquets qui sortent vers l'OPNsense. Le trafic client2 ↔ client3 n'est pas traduit.
  • ip saddr 10.10.2.0/23 : uniquement pour les paquets venant des réseaux clients. Un /23 regroupe deux /24 consécutifs : 10.10.2.0 à 10.10.3.255, soit exactement vmbr2 et vmbr3 en une seule règle.
  • masquerade : remplace l'IP source par l'IP actuelle de eth0. Contrairement à snat to, il n'y a pas besoin de connaître l'adresse à l'avance, ce qui est idéal puisqu'eth0 est en DHCP.

Trajet complet d'un ping vers Internet

Double NAT : la box traduit une première fois, l'OPNsense une seconde fois.

Comment la réponse retrouve son chemin : conntrack

Le noyau garde une table de suivi des connexions (connection tracking). Quand la box masque la source d'un paquet, elle mémorise « 10.10.2.131 parle à 1.1.1.1, traduit en 10.0.0.137 ». Quand la réponse revient, elle consulte cette table et restaure automatiquement la bonne destination. On n'écrit aucune règle pour le retour : c'est implicite. On peut observer cette table avec conntrack -L (paquet conntrack).

Le calcul du /23

En binaire, 10.10.2.0 et 10.10.3.0 ne diffèrent que par le dernier bit du troisième octet (00000010 et 00000011). En fixant 23 bits au lieu de 24, on laisse ce bit libre : le préfixe couvre les deux réseaux. C'est une agrégation de routes (supernetting), le même principe qu'utilisent les routeurs pour résumer plusieurs réseaux en une seule entrée.

Voir le masquerade en direct

Sur la box, lance tcpdump -ni eth1 icmp dans un terminal et tcpdump -ni eth0 icmp dans un autre, puis fais un ping depuis client2. Sur eth1 tu vois l'IP 10.10.2.x, sur eth0 la même requête apparaît avec l'IP 10.0.0.137 de la box.

9Service DHCP

Le DHCP distribue automatiquement aux clients leur adresse IP, leur masque, leur passerelle et leur serveur DNS. On utilise dnsmasq, un logiciel léger qui fait à la fois DHCP et DNS, ce qui correspond exactement au rôle de la box sur le schéma.

box 
apt install -y dnsmasq
/etc/dnsmasq.d/lab.conf 
interface=eth1
interface=eth2
bind-interfaces
domain=lab.local
no-resolv
server=10.0.0.254
dhcp-range=10.10.2.100,10.10.2.200,255.255.255.0,12h
dhcp-range=10.10.3.100,10.10.3.200,255.255.255.0,12h
systemctl restart dnsmasq
systemctl status dnsmasq --no-pager
DirectiveEffet
interface=eth1
interface=eth2		dnsmasq n'écoute que sur les réseaux clients. Il ne doit surtout pas répondre sur eth0, sinon il entrerait en concurrence avec le DHCP de l'OPNsense sur vmbr1.
bind-interfacesSe lie explicitement à ces interfaces au lieu d'écouter sur toutes les adresses.
no-resolvIgnore /etc/resolv.conf de la box pour choisir le serveur DNS amont.

Pourquoi pas d'option routeur ni DNS ?

Par défaut, dnsmasq annonce comme passerelle et comme DNS l'adresse de l'interface sur laquelle il répond. Un client de vmbr2 reçoit donc 10.10.2.1, un client de vmbr3 reçoit 10.10.3.1. C'est exactement ce qu'on veut, sans rien ajouter.

L'échange DHCP : DORA

sequenceDiagram

  participant D as dnsmasq sur box eth1

Discover, Offer, Request, Acknowledge : les quatre messages d'une attribution DHCP.

Pourquoi un serveur DHCP par réseau ?

Le DISCOVER est un broadcast : il ne traverse pas les routeurs. Un client de vmbr2 ne peut donc jamais atteindre le DHCP de l'OPNsense. C'est pour ça que le schéma place un serveur DHCP sur la box, qui est présente physiquement sur chaque réseau client. L'alternative serait un relais DHCP sur la box qui retransmet les requêtes à un serveur central.

10Service DNS

Le DNS traduit les noms (debian.org) en adresses IP. dnsmasq, déjà installé pour le DHCP, fait aussi office de serveur DNS cache et relais pour les clients.

Il répond de deux façons :

  • Noms locaux (client3.lab.local) : il répond directement, grâce aux noms que les clients lui ont communiqués lors de leur requête DHCP.
  • Noms externes (debian.org) : il relaie la question au serveur fixé par server=10.0.0.254, c'est-à-dire l'OPNsense, puis met la réponse en cache. Grâce à no-resolv, ce choix ne dépend pas du resolv.conf de la box, qui pourrait changer au gré du DHCP.

Chaîne de résolution : client, box, OPNsense, Internet.

Pourquoi un DNS sur la box plutôt que d'envoyer les clients directement vers l'OPNsense ?
  • Seul le serveur DHCP connaît les noms des clients : c'est donc lui qui peut résoudre client2.lab.local.
  • Le cache local réduit le trafic et accélère les résolutions répétées.
  • La box est la seule machine directement joignable depuis les réseaux clients, c'est le point naturel pour les services réseau de base.
Tester la résolution

Depuis un client : dig debian.org (paquet bind9-dnsutils). La ligne SERVER: en bas de la réponse doit indiquer 10.10.2.1 ou 10.10.3.1. Pour un nom local : dig client3.lab.local.

Les clients n'ont presque rien à configurer : il suffit de régler leur carte net0 sur IPv4 : DHCP dans Proxmox. Tout le reste leur est fourni par dnsmasq.

L'adresse et la route par défaut sont fournies par dnsmasq. Le bloc BEGIN PVE dans resolv.conf montre que Proxmox gère aussi ce fichier dans les conteneurs, à partir de l'onglet DNS du conteneur. Si on change le plan d'adressage, on ne modifie que la box : les clients suivent au prochain renouvellement de bail.

Lire le TTL pour prouver le routage

Linux envoie ses paquets avec un TTL de 64, et chaque routeur traversé le décrémente de 1. Une réponse de la box elle-même arrive donc avec ttl=64, une réponse de l'OPNsense avec ttl=63 : il y a exactement un routeur entre les deux, la box. Même logique pour 1.1.1.1 : ttl=53 depuis la box, ttl=52 depuis un client, soit un saut de plus. Le ping de client3 vers client2 en ttl=63 prouve que le trafic entre les deux LAN passe par la box sans aller jusqu'à l'OPNsense.

13Incidents et dépannage

Incidents rencontrés pendant le TP

1. dnsmasq en échec au démarrage

systemctl is-active dnsmasq renvoyait failed. La configuration désignait des interfaces ens19 et ens20, noms typiques d'une VM virtio, alors que la box est un conteneur dont les interfaces s'appellent eth1 et eth2. Avec bind-interfaces, dnsmasq refuse de démarrer sur une interface inexistante.

sed -i 's/ens19/eth1/; s/ens20/eth2/' /etc/dnsmasq.d/lab.conf
systemctl restart dnsmasq

2. Clients sans adresse IPv4

client2 n'avait qu'une IPv6 link-local et aucune route : Network is unreachable sur tous les pings. Les clients avaient démarré pendant que dnsmasq était en panne : leurs requêtes DHCP étaient restées sans réponse et ils avaient abandonné. Après vérification que la carte était bien en IPv4 DHCP dans Proxmox, un Shutdown puis Start a suffi à obtenir un bail.

Leçon : l'ordre de démarrage compte

Un service réseau doit être opérationnel avant ses clients. En production, on règle l'ordre de démarrage dans Options › Start/Shutdown order de Proxmox : OPNsense d'abord, puis la box, puis les clients.

3. Tester depuis la bonne machine

Une première série de pings a été lancée depuis la box au lieu d'un client. Elle réussissait, mais ne prouvait rien sur le forwarding ni le NAT, puisque les paquets ne traversaient pas la box. Les tests de routage doivent toujours partir d'une machine située derrière le routeur.

14Limites et améliorations

Filtrage : la box ne filtre rien

En l'état, la box route tout, y compris entre les deux réseaux clients. Pour un vrai cloisonnement, on ajouterait une table de filtrage avec une politique « tout interdit sauf » :

ajout possible à /etc/nftables.conf 
table inet filter {
  chain forward {
    type filter hook forward priority 0; policy drop;
    ct state established,related accept      # réponses autorisées
    iifname { "eth1", "eth2" } oifname "eth0" accept   # clients vers l'extérieur
    # pas de règle eth1 <-> eth2 : les deux LAN sont isolés
  }
}
Le principe du moindre privilège

Chaque réseau ne devrait pouvoir parler qu'à ce dont il a besoin. Si client2 est compromis, l'isolation empêche l'attaquant de rebondir directement sur client3 : c'est la base de la segmentation réseau.

Supprimer le double NAT

Au lieu de masquer les clients sur la box, on peut donner à la box une IP fixe sur vmbr1 (elle a aujourd'hui 10.0.0.137 par DHCP, qui peut changer) et ajouter sur l'OPNsense des routes statiques : 10.10.2.0/23 via l'IP fixe de la box. L'OPNsense voit alors les vraies IP des clients, ce qui permet des règles de pare-feu et des journaux par machine. Il faut penser à inclure ces réseaux dans le NAT sortant de l'OPNsense.

Services séparés

dnsmasq convient très bien à une maquette. En production, on séparerait souvent les rôles : Kea pour le DHCP (successeur d'ISC DHCP) et BIND9 ou Unbound pour le DNS, avec mise à jour dynamique des enregistrements.

Réservations DHCP

Pour qu'une machine garde toujours la même IP sans configuration statique : dhcp-host=BC:24:11:xx:xx:xx,client2,10.10.2.10 dans la configuration dnsmasq.
